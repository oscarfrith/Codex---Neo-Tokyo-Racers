# Reusable validation and handoffs

Choose checks by the changed behaviour, using scripts/validation_checks.json as the reusable procedure catalogue. It contains tooling/install, normal start, garage/race transitions, errors, cleanup, API-only, streaming, physical-device, multiplayer and persistence recipes. Do not run everything for a copy edit. These recipes are instructions for observed testing, not automatic gameplay bots or proof that a historical run passed.

The acceptance contract for this workflow is repository-only: preserve all gameplay, state/geometry/visibility/preview/attachment owners, inputs and saved data. Reuse the existing capture and runtime samplers. Add selected evidence records with explicit pending/deferred outcomes and compact handoffs; do not create runtime systems, new remotes or backup instances. Device and persistence behaviour are unchanged. Done means the recorder rejects misleading evidence categories, tests pass and future assistants have repeatable procedures. This does not close game acceptance gates.

## Assistant-operated loop

1. Read current status and choose only applicable checks. For tiny tasks a focused check and short final response remain enough; structured records are useful for connected, repeated or deferred work. Decide expected outcomes and applicable device/input/load targets before testing. Check selection still requires judgement.
2. Create a task record: `python scripts/validation_record.py init docs/architecture/TASK-validation.json --task "Task name" --checks installation startup garage errors cleanup`. All results start pending. Fill build identity (commit plus working changes or capture fingerprint), scope, Studio action, capture date/scope, recovery and next action.
3. Run selected procedures. Start with fresh normal Play and verify the visible start flow before UI checks. Inspect existing startup state; do not require gameplay modules through MCP. Record session, build, UTC time, environment, device and input. Mutating API/fault tests require the existing no-save sandbox or a specifically authorised isolated published test environment. Never enable production saving just to satisfy a check.
4. Store raw output, screenshots or a factual observation log under the task's repository evidence directory. Notes must identify observer, time, action, expected/actual result and limits. Pin a file using `python scripts/validation_record.py artifact PATH` and put the returned path/SHA256 in the check's evidence list. This checks integrity, not truth or sufficiency. Before pinning text, use stable LF checkout rules in .gitattributes and normalise once; byte-exact raw/binary evidence must use -text. Verify staged bytes match the pins so another machine can validate them. Preserve original evidence; a corrected observation gets a new file.
5. Mark each selected check pass/fail/pending/deferred/not-applicable. Pass/fail needs observations and pinned evidence. Any non-pass needs a reason; open checks also need a next action. UI passes require `interaction: normal-ui`, `start_screen_active: false`, `visible_input_verified: true`. Physical-device passes require `environment: physical-device`. Published multiplayer/persistence require `environment: isolated-published`; persistence also requires saving_enabled=true. Load tests declare actual and required players/minutes. Do not lower the approved target to make a run pass.
6. Run `python scripts/validation_record.py check RECORD`. Exit 0 means selected checks resolved, 2 means open checks remain; malformed/inconsistent records fail. Open records are valid handoffs, never evidence of programme completion. Run `handoff RECORD` to produce a compact summary, save it under docs when useful, then review it. Keep 00_START_HERE as the sole current-status owner; dated reports are evidence, not a second run queue.

The assistant runs these steps and authorised Git operations. The user is only needed for unavailable environments, subjective gameplay acceptance or missing requirements. No recurring monitoring, auto-deployment or automatic game-wide acceptance is introduced. Git commit/push outcomes belong in the final handoff after they actually succeed, not in an advance promise inside a generated report.

## Reuse existing measurement tools

- scripts/performance_phase1/runtime_sample.lua: bounded eight-second Client/Server sample during Play; startup attributes, parented counts and frame intervals. It does not require gameplay modules or invoke remotes. Counts/scans are outside the timed sample. Studio intervals/memory are not physical-phone performance or CPU attribution.
- scripts/performance_phase6/api_cycles.lua: five API cycles only, with an owned sandbox vehicle. It changes runtime state through existing APIs; it is not a read-only audit or normal-flow test. Inspect prerequisites before invoking and stop on failure. Never use its success to populate garage/race/UI passes.
- scripts/studio_capture.py and relevant projection/audit checks: installation/source/config evidence. Capture only the needed hierarchy/properties alongside source inventory. Normal runtime sampling does not require a full mirror refresh.
- MCP console/scene inspection: retain session/time boundaries and before/after snapshots. Native/known errors still appear in the report with issue IDs. A single scene snapshot cannot establish a leak or resource plateau.

Cleanup comparisons need the same build, flow, batch size and settled interval. Repeat the normal visible flow, including cancellation, destruction and stream-out where relevant. Track detached objects/connections when observable; otherwise explicitly defer that claim. Do not inject forced garbage collection or a new owner to manufacture stable counts.

## Handoff and laptop continuation

Record what changed; generated versus installed versus tested versus user-confirmed; pass/open checks and evidence; exact outstanding Studio script or none; capture freshness/scope; recovery and next action. Pin source/capture references and leave devices/load/save gates open when unavailable. General “works well” feedback belongs as general confirmation, not retroactive specific test results.

For another machine: push verified work, pull the same branch, open the intended saved Space Racers place and connect Studio MCP. Verify place ID and mode again; local Studio files do not transfer through Git unless deliberately saved there. Discover the local Python executable instead of copying another machine's cache path. Read 00_START_HERE and the relevant task record, inspect Git/live drift and continue only the approved work. Do not rerun old installers or full exporters merely because the machine changed.

The record validator enforces categories, required metadata and artifact integrity. It cannot judge screenshots, prove device identity, enforce the completeness of selected checks or certify an observer's claims. Review those explicitly. No game-wide acceptance status is generated.
